## B. 播放与解码

项目主线的核心。**全部功能都建立在"能正常听歌"之上。**

- [ ] 📐 **T-B01 解码器接口**
  `Decoder::open/read/seek`，单线程契约、无内部锁。

- [ ] 📐 **T-B02 音频输出接口**
  `RenderCallback` 契约写死在注释里：实时线程、禁分配/锁/阻塞/日志/异常、必须恰好填满 `frame_count`。违反契约表现为爆音或死锁，事后极难查，所以契约必须写在头文件里而不是 wiki 里。

- [ ] 📐 **T-B03 时基方案：设备即时钟**
  在设备回调里拉帧，解码慢表现为 underrun 而不是双时钟漂移。交叉淡化和 gapless 都依赖这一点。

- [ ] **T-B04 FFmpeg 解码后端**
  依赖：FFmpeg 开发库（未安装）。

- [ ] **T-B05 WASAPI 输出后端（共享模式）**
  Windows 第一版够用。独占模式留到 v0.5。**独占不等于位精确**，两者是两个档（见 T-B15）。

- [ ] **T-B06 音频文件格式支持**
  已列出 21 种扩展名：mp3/flac/ogg/oga/opus/m4a/mp4/aac/wav/aiff/aif/ape/wv/wma/dsf/dff/mka/m4b/caf/w64/tta。实际能播几种取决于 FFmpeg 编译配置。

- [ ] **T-B07 元数据读取（TagLib）**
  标题、艺术家、专辑、时长、封面。

- [ ] **T-B08 封面缓存**
  缩略图按需生成，不每次读原图（一张 3000×3000 的封面解码要几十毫秒，列表滚动会卡）。

- [ ] **T-B09 拖拽进度条预览、松手才 seek**
  拖动时显示预览时间，只在松手时真正 seek。否则每移动 1 像素发一次 seek，解码器被打爆。

- [ ] **T-B10 键盘快捷键**
  空格播放/暂停、方向键跳转。

- [ ] **T-B11 记忆上次状态**
  音量、播放模式、窗口布局。

- [ ] **T-B12 gapless 播放（预解码下一首）**
  v0.5。

- [ ] **T-B13 交叉淡化 0–12 秒可调**
  v0.5。

- [ ] **T-B14 10 段图形均衡器 + 预设**
  v0.5。

- [ ] 📐 **T-B15 输出模式三档：`Shared` / `Exclusive` / `BitPerfect`**
  `OutputMode` 枚举已扩成三个值（`core/include/mp3/audio_output.h`）。三档的分界线不是"谁更强"，而是**承诺什么**：

  | 档 | 拿到什么 | 没承诺什么 |
  | --- | --- | --- |
  | `Shared` | 一定成功，能和其他 App 同时出声 | OS 可任意重采样、加效果、过音量 |
  | `Exclusive` | 独占设备（别人抢不走，也抢不走别人） | **不保证位精确**——驱动内部仍可能转换，系统音量仍可能挂在路径上 |
  | `BitPerfect` | 独占 + 承诺样本不被改动：不加软件音量、不重采样、流格式必须等于设备原生格式 | 不承诺一定成功 |

  **`BitPerfect` 协商失败必须报错，不能静默降级。** 静默降级比不支持更糟：用户以为在听直通，实际 OS 在偷偷重采样，而且他永远不会知道。这条是 `open()` 契约，写进了头文件注释。

  **设置项**：`audio.output_mode`（枚举，默认 `Shared`，scope `device`）。必须是 `device` 作用域——PC 上的独占设置推到手机上毫无意义（设备名都不一样），而且会导致手机端打不开设备直接哑掉。

- [ ] 📐 **T-B16 不同采样率连播：每次采样率变化就重开流（方案 A）**
  曲目 44.1k → 96k 连播时，两种做法：①重开设备流到新采样率；②把所有曲目重采样到固定率。**定案①**，理由是采样率直接决定听到什么，而重开的代价只是一次短促的断点。

  **这条只在 `Exclusive` / `BitPerfect` 下有意义。** `Shared` 模式下流格式就是 OS 混音格式（Windows 通常是 48k 固定），重开只是把同一件事再做一遍，所以共享模式始终一条流、由 OS 重采样。

  **必须写明的两个后果**：
  1. **采样率变化的边界处不可能 gapless，也不可能交叉淡化。** 同一采样率的相邻曲目两者都照常工作（T-B12/T-B13 不受影响）；跨采样率的边界就是一段几百毫秒的静默。这是有意接受的代价，不是 bug。
  2. 重开流期间必须保证不出现爆音：先 `stop()`，`close()`，`open()` 新格式，`start()`，全程由解码线程预填缓冲区，不能让声卡回调拿到半截数据。

- [ ] **T-B17 Android USB DAC 位精确直通（「遥遥无期」档）**
  不是 v0.x 的事，只是记在案。Android 14+ 有 `setPreferredMixerAttributes()` + `MIXER_BEHAVIOR_BIT_PERFECT`，但：

  - 它是**可选设备特性**，厂商要在 `usb_audio_policy_configuration.xml` 的动态 mix port 上挂 `AUDIO_OUTPUT_FLAG_BIT_PERFECT`，绝大多数手机没有。
  - 该模式下**框架不提供软件音量**，音量必须由硬件控制，UI 得跟着改。
  - 实测连锁：Pixel 9 Pro XL（Android 17）上 YouTube Music 恒走 48k 混音器、Apple Music 到 192k 但 `BitPerfect=false`、Tidal 直接是 16 位 AudioTrack。Google issue tracker 上报告者的原话是 "It's purely an adoption problem."

  **结论**：Android 只承诺"尽力提升"——默认走 AAudio 原生采样率，能试 bit-perfect 就试，失败静默回落到 `Shared`（这一处允许回落，因为它本来就是尽力而为，与我们自己的 `BitPerfect` 档契约不矛盾）。DSD 在 Android 上只能走 DoP，原生 DSD 不做。

## C. 曲库

- [ ] 📐 **T-C01 数据模型定案**
  `tracks` / `artists` / `albums` 规范表 + 保留原始标签字符串。`album_artist` 与 `track_artist` 必须分开，否则合辑要么全标 Various Artists、要么碎成 N 张单曲。完整建表语句见 [DATA_MODEL.md](DATA_MODEL.md)。

  **曲库不同步（见 T-E14）。** 所以 `artists` / `albums` / `tracks` / `track_files` 都是本机私有的扫描缓存：没有 `uid`、没有 `updated_at`、没有 `deleted_at`，怎么删怎么重建都不影响对端。跨设备能对齐的只有两个**函数**——`fingerprint`（文件身份）和 `work_key`（统计聚合），两端各算各的，算出来一定一样。

- [ ] 📐 **T-C02 文件夹层级浏览：不建 `folders` 表**
  用 `track_files.folder_path` + `file_name` 两列索引，UI 按路径公共前缀分组。
  **不建表的理由：目录没有身份。** 重命名文件夹是"改名"还是"删除+新建"？没有 `uid` 无法回答；一旦给了 `uid` 就要处理同步和墓碑，成本翻倍。用路径反推，重命名就是路径变了，扫描器自然处理。
  代价：无法显示空文件夹。对音乐播放器没有影响。

- [ ] 📐 **T-C03 一首曲目对应多个文件（`track_files` 表）**
  同一个音频文件可能同时存在于 `D:\音乐\` 和 `D:\下载\`。路径不能放在 `tracks` 上，否则删掉一份歌就没了。
  拆表后：一条曲目 → N 个文件行；删掉一份另外一份照常播。`present` 布尔量标记"上次扫描没见到"，配合 `(size, mtime)` 识别重命名——实测改名后行数仍是 1，不会变成"删一个加一个"。
  **文件丢失不等于用户删除。** 文件丢失是 `tracks.has_local_file = 0`（记录保留，等你插回移动硬盘），用户主动删除是 `DELETE tracks` 行。曲库不同步之后这里反而简单了——不需要墓碑，因为删歌不用传播。混用会导致真实故障：拔掉移动硬盘 → 扫描把全部歌标记删除 → 插回去墓碑挡住恢复。

- [ ] 📐 **T-C04 扫描策略：剥标签取指纹 + 增量扫描**
  指纹从「文件大小 ‖ 前 256KiB ‖ 后 256KiB」改为**先剥掉 ID3v2/APEv2/ID3v1 再对纯音频区间取哈希**。实测同一首音频在 5 种标签组合下指纹完全一致；原先的写法给文件写 217 字节 ID3v2 标签后指纹就变了，同一首歌变成两首。
  代价：文件中间音频数据的改动检测不到（头尾法本来就检测不到），对音乐播放器无影响。
  扫描时机：设置页提供手动扫描按钮，另加「启动时扫描变更」开关（默认开）。不做文件系统监听——Windows 监听 8 万目录会出问题，Android 的 SAF 根本不支持。
  性能实测：纯 `stat` 枚举 10 万文件 3.0 秒；头尾各 256KB 指纹 0.5 ms/首；全量写库 10 万行 506 ms。**增量必须做到"文件没变就不算指纹"**，否则每次启动要读几十 GB。

- [ ] 📐 **T-C05 扫描增量判断：低精度文件系统用 racy 保护**
  NTFS 的 mtime 粒度实测约 100 ns（设定间隔 10 ns 区分不出、100 ns 能区分）；但 **FAT32 是 2 秒、exFAT 是 10 毫秒**。音乐库放在移动硬盘上时，2 秒内连续改两次会漏检——扫描时记下 mtime=10000，等到 10800 再改，mtime 仍落在 10000 这一格，下次扫描认为"没变"。

  **定案：不探测文件系统类型，一律按最坏的 2 秒。** 每个文件多存一列 `fp_verified_at`：

  ```text
  可疑 ⇔ (已存 mtime + 2000ms > fp_verified_at) 且 (已存 mtime <= 本次扫描时刻)
  fp_verified_at = max(本次扫描开始时刻, 该文件当时的 mtime)
  ```

  第二个条件不能省——**未来 mtime 的文件会让第一个条件恒真**，于是每次扫描都重算，永远停不下来。加上它之后第 1 次算完就稳定。

  实测代价：20000 首真实感曲库误判重算 **0 首**；批量导入 300 首后一小时内多算 300 个，约 **0.15 秒**（0.5ms/首）。而配置里 `library.scan_delay_seconds = 30`（扫描在启动 30 秒后才开始），这点代价基本归零。

  另一个必须打的补丁：**算指纹前后各 `stat` 一次，两次结果不一致就放弃这一轮**，不写库——否则会把"读的过程中被改了一半"的文件指纹当成稳定值存下来。

- [ ] **T-C06 搜索：先用 `LIKE`，别急着上 FTS5**
  原计划 FTS5 + `trigram` 分词器。**我实测后推翻了。** FTS5 的 trigram 按三字符滑窗建索引，**查询串短于 3 字符完全匹配不到**：

  | 查询 | trigram 结果 | LIKE 结果 |
  | --- | --- | --- |
  | `夜`（1 字） | 空 | 命中 |
  | `夜曲`（2 字） | **空** | 命中 |
  | `晴天`（2 字） | **空** | 命中 |
  | `稻香`（2 字） | **空** | 命中 |
  | `七里香`（3 字） | 命中 | 命中 |

  中文歌名两字极多，搜「晴天」返回空白不可接受。而 `LIKE '%…%'` 在 20000 行曲库上全表扫描仅 **1.2 毫秒**（10 万首约 6–10ms）。
  → 改为普通表 + `LIKE` + 150ms 防抖 + 结果上限 200。
  将来若上 FTS5，应用 `unicode61` + 自己实现中文二元组分词，**不用 trigram**。

- [ ] 📐 **T-C07 跨设备曲目身份：`fingerprint`**
  **先剥掉 ID3v2 / APEv2 / ID3v1 标签，再对纯音频区间取** `SHA-256(音频长度 ‖ 前 256KiB ‖ 后 256KiB)`。与路径、修改时间、设备、标签全都无关；40MB 的 FLAC 只读 512KB。
  **为什么要剥标签：** 实测给文件写 217 字节 ID3v2 标签，头尾哈希立刻变，同一首歌变成两首，播放次数和评分全丢。而改标签、补封面、回写 ReplayGain 每天都在发生。剥标签后同一段音频在 5 种标签组合下指纹完全一致（裸音频 / ID3v2 200B / ID3v2 3000B / +APEv2 / +APEv2+ID3v1），代价为零——仍然只读 512KB，只是把起点挪过标签头、终点挪到标签之前。
  局限一：同曲不同编码版本（FLAC vs MP3）指纹不同，视为两个文件。**这是有意的**——音质不同确实是不同的东西。
  局限二：文件中间音频数据的改动检测不到。头尾法本来就有这个盲区，对音乐播放器无影响。

  **⚠️ 别用「文件名（不含扩展名）」做标识。** 实测 17 个真实感文件只产生 8 个不同 basename，**5 个冲突**：`01` 被 4 个专辑的第一首共享、`晴天` 被 mp3/flac/Live/伴奏四份共享、`安静` 是周杰伦原版 + 翻唱、`童话` 是光良 + 儿歌、`月光` 是贝多芬 + 古典合集。而且它想救的"换版本"场景只救得了 1/6（`晴天.mp3`→`晴天.flac` 可以，`晴天 (FLAC 无损).flac` / `01. 晴天.flac` / `周杰伦 - 晴天.flac` / `Track01.mp3`→`01 - 晴天.flac` 全不行）。

- [ ] **T-C08 名称归一化与排序**
  匹配键：NFC → 小写 → 去变音符号 → 折空白 → 去开头 `The`。用于判断"是不是同一个人"，**原始标签串必须保留在 `name` 列**，否则用户看到的歌名和你库里的不一样。

  各步边际收益（30 个真实艺术家）：原样 81 个 → 加 NFC+小写+折空白 **49**（单独消灭 32 个重复）→ 再加去变音 46（+3）→ 再删 The **39**（+7）。去变音收益最小但零成本，保留。

  **删除 `sort_name` 列**：纯 ASCII 下它与 `name_norm` 排序结果完全相同；带变音符号时**反而更差**——`sort_name` 保留 `ö`(U+00F6)，SQLite 按码位排到 `z` 之后，`Björk` 掉到 B 区末尾。删掉后英文排序直接 `ORDER BY name_norm`。

  有意不合并的（需要别名表/繁简表，另开设计）：`Simon & Garfunkel` vs `Simon and Garfunkel`、`AC/DC` vs `ACDC`、`简体周杰伦` vs `繁体周傑倫`、`五月天` vs `MAYDAY`。

- [ ] **T-C09 时长存毫秒**
  不存秒。理由：`duration_ms` 是 seek 的乘数，截断到秒会让每次 seek 固定偏最多 1 秒；也是曲库总时长的被加数，1000 首累计偏差约 9 秒。存储成本：SQLite INTEGER 是变长编码，`221400` 占 4 字节 vs `221` 占 3 字节，十万首差 100KB。

- [ ] 📐 **T-C10 统计聚合键：`work_key`**
  `work_key = norm(artist) + "\x1f" + norm(title)`，`norm` 做 NFKC 全角转半角 → `casefold()` → 去空白 → 去标点 `[\s\-_·・.,，。、!！?？'"“”‘’()（）\[\]【】]`。

  它和 `fingerprint` 是**两件事，不能合并**：`fingerprint` 管"这个文件是谁"，`work_key` 管"这段音乐是哪首作品"。换版本（MP3→FLAC）指纹变了、作品键不变，于是曲库里是两条，统计里是一条。

  | 场景 | 合并？ |
  | --- | --- |
  | `晴天/周杰伦` → `晴天/周杰伦 `（尾部空格） | ✅ |
  | 全角括号 → 半角括号 | ✅ |
  | `Qing Tian/Jay Chou` → `qing tian/jay chou` | ✅ |
  | 繁体 `周杰倫` → 简体 `周杰伦` | ❌ 分开 |
  | `晴天` → `晴天 (Live)` | ❌ 分开（有意） |

  **不带专辑。** 带上专辑碰撞能降到 0，但「精选集换成原版专辑」这个最常见的换版本场景会断开——这恰好是它要解决的问题。
  **不剥括号。** 剥了会把 `(Live)`、`(Acoustic)`、`(Remastered 2011)` 一起剥掉。现场版是不同时间地点真实听到的另一段演出，分开更诚实。
  **无标题标签 → 归为「未识别」，`stats_key` 退回 `fingerprint`、`identified = 0`。** 实测硬用文件名兜底：500 个 `01.mp3`/`Track01.mp3` 类命名只产生 80 个键，**平均每键 6.2 个文件被错合并**，所以文件名不能当键。但"这首没名没姓的歌我听了 12 次"是真实发生的，不该蒸发——所以计入总量、不进排行榜（见 T-D11）。
  **碰撞不处理。** 5000 首真实感模型里 4500 个作品键中 4372 个只含 1 首（98.7%），最大的键也只有 3 个文件，都在"爆款歌被多张合辑收录"的合理范围内。

- [ ] 📐 🧑 **T-C11 编辑曲目标签**（🧑 你要求的功能）
  设置里提供入口：读出文件内的标签显示，改完写回文件，然后重新读取该曲目信息。

  **改的是文件，不是数据库。** 库是本机缓存，文件才是真源——写的顺序必须是"写文件 → 更新库"。反过来先改库，下次扫描会被文件覆盖回去，用户看到"改了又变回来"。

  **不需要重算指纹。** 指纹算的是**音频区间**（剥掉标签后），写标签不动音频，指纹值不变。要跟着更新的只是 `tracks.file_size`/`file_mtime` 和 `track_files.fp_size`/`fp_mtime`/`fp_verified_at`——它们是"下次扫描要不要再读盘"的判据，不是指纹本身。实测改完标签连做三次增量扫描：三项都不更新 → 第一次重算、后两次不重算；三项都更新 → 一次都不重算。

  **一次编辑只改一个文件。** 同一首歌可能有多个 `track_files` 行（多份拷贝，见 T-C03），但标签是落实在文件本身上的，所以只改用户点开的那个文件，不替他"顺便全改"。

  **指纹不会因为改标签而变**——这是整个功能的安全基石。实测同一段音频在 6 种标签形态下指纹完全一致：ID3v2 标签体 200 → 3000 → 40000 字节，音频区间从 `0..600000` 挪到 `40010..640010`，指纹始终是 `9b0a4c3745406782`；尾部加 APEv2、再加 ID3v1 也一样。由此推出三件用户能直接感到的好处：

  | 因为指纹不变… | 结果 |
  | --- | --- |
  | 重扫不新建曲目行 | 编辑后不会在列表里多出一条"重复的" |
  | `tracks.id` 不变 | `track_files` / `track_artists` / `playlist_items.track_id` 三处外键全部继续有效 |
  | 内容身份不变 | `track_ratings`（键 `fingerprint`）和 `playlist_items.ref_fingerprint` 全部继续有效 |

  **唯一会变的是 `work_key`**（「艺术家 + 标题」的归一化结果）。改了标题之后，`play_stats` 里挂在旧键上的次数就搜不到了。**这个残留不处理**（不迁移汇总行、不加别名表）：迁移在两端各自执行时容易搬两遍（迁移本身没有幂等键），别名表要为低频操作引入一张永久同步表；而残留是"可见但不误导"的——统计页会显示「晴天 42 次」和「晴天修正版 3 次」两行，而不是错误的合并数字。

  写回的两个约束：写之前重新读一次原文件标签（不能拿库里可能过期的缓存去覆盖）；写失败（只读 / 被占用 / 磁盘满）必须报错并保持原文件不动——宁可不改，也不能写坏文件。

- [ ] **T-C12 中文拼音排序键 `pinyin_key`**
  中文按 `name_norm` 排是**码位序**不是拼音序：实测得到 `五月天 周杰伦 张学友 李荣浩 林俊杰 王菲 薛之谦 邓紫棋 陈奕迅`，用户期望 `陈奕迅 邓紫棋 林俊杰 李荣浩 王菲 五月天 薛之谦 张学友 周杰伦`。

  方案：自带 6763 字拼音表（紧凑 **16 KiB**：2 字节音节编号 + 音节字符串池），扫描时算出 `pinyin_key = "zhou\x00jie\x00lun"`，`ORDER BY pinyin_key` 走覆盖索引 **0.01 ms**（2 万行取前 50）。

  **为什么不注册自定义 collation**：实测同样查询用 `COLLATE PINYIN` 是 **3.61 ms**（临时 B 树全量排序，慢 361 倍）；给 collation 建索引虽能到 0.01 ms，但**该索引在未注册 collation 的连接上查询会直接报错**（备份换设备打开就崩）；且 Windows 用 `CompareStringEx`、Android 用 ICU `Collator`，两端可能排出不同顺序。

  **必须逐字比较，不能整串拼接**：`李荣浩`(`lironghao`) vs `林俊杰`(`linjunjie`) 整串拼接得出 `lin < lir` → 排反了；逐字比较 `li` 是 `lin` 的前缀 → 正确。用 `\x00` 分隔拼接等价于逐字比较。

  **多音字按第一读音固定**（不猜「重庆」/「重复」），超出字典按码位兜底。列现在就在表里（可 NULL），**v0.3 扫描时才填值**。

## D. 播放历史与听歌统计

🧑 **你的要求**：记录"你听过最多次的歌"、"你的总听歌时长"这类整合信息。

- [ ] 📐 **T-D01 播放记录参与同步**（🧑 你定的）
  原来是"设备本地、不同步"，改掉了。

- [ ] 📐 **T-D02 计数绝不冗余存在 `tracks` 表里**
  这是最容易犯的错。给 `tracks` 加一列 `play_count`，播一次加一，单机没问题，**一同步就彻底错了**：PC 听 10 次、手机听 5 次，同步按"取最新"合并，结果是 10 或 5，**都不是正确的 15**。

  我写了模拟验证：

  | 方案 | 结果 | 对吗 |
  | --- | --- | --- |
  | 计数器列 + last-write-wins | **5** | ❌ 丢掉另一台的收听 |
  | `play_history` + 聚合 | **15**（两端一致） | ✅ |

  所以 `play_count` 永远是**从播放记录聚合算出来的**。这也是播放记录必须同步的真正原因。

- [ ] 📐 🧑 **T-D03 播放次数阈值设置，默认 50%，判定写入时冻结**（🧑 你的想法①；"只做增量、不随阈值变化"是你后来改的方向）
  设置项：听多长时间（按歌曲百分比）才算听了一次。**默认 50%。**

  **判定在写入记录的那一刻做完，结果存进 `play_history.counted` 列，之后永不重算。**

  ```text
  写入时：counted = (played_ms * 100 >= duration_ms * 当时的阈值) ? 1 : 0
  统计时：count(*) WHERE counted = 1
  ```

  **为什么你否掉"追溯生效"是对的——三条我自己验证出来的理由：**

  1. **重算会让历史数字变来变去。** 用户看到「晴天」听了 42 次，把阈值从 50% 调到 90%，第二天变成 31 次。同一个软件、同一份历史，两次看两个数，这是 bug 的表现而不是功能的表现。
  2. **重算和增量同步天然冲突。** 记录是跨设备合并的。如果每台设备按自己的设置重算，PC 和手机会对同一条记录得出不同的 `counted`——同步时这条到底算不算？没有正确答案。而把决定写进行里，它就是一条**普通数据**，同步规则不需要为它开特例。实测：PC 用 50%、手机用 90%，合并 6 条记录后 PC 数出 3 次，每条带着自己的判定一起过来，再同步一遍数字不变。
  3. **重算需要永远保留全部原始记录。** 不重算就没有这个约束，清理策略可以独立决定（见 T-D05）。

  **代价（写清楚）：** 阈值从 50% 调到 90% 之后，90% 只对**新听**的歌生效。这是有意取舍——统计口径应当稳定，不随设置漂移。

  **设置项描述必须写「更改阈值不会改变以前的计数」**（🧑 你定的）。用户改了阈值发现旧数字没变小，第一反应会是"设置没生效"或"软件坏了"；这一句话提前把预期摆正。

  **但统计页面不加任何解释文字**（🧑 你定的）：统计页是看数字的地方，加脚注会把它变成说明书。想知道的人去设置里看，不想知道的人不该被打断。

  所以 `play_history` 有两列：`counted`（0/1，判定结果）和 `count_threshold`（当时用的阈值，仅供排查"为什么只听了 40% 却算了一次"）。

  **⚠️ 判据仍然是比例，不能是 `end_reason='completed'`。** 一首 4 分钟的歌听到 90% 跳过，`end_reason` 记的是 `'skipped'`，但在 50% 阈值下它**应该**算一次播放。

  **这顺带解决了 T-D05 原来那个直方图的坑：** 因为不再从 `played_ms/duration_ms` 反推判定，清理原始记录时只要把 `counted` 已经算进汇总，就永远不会有"阈值改了但历史失去信息"的问题。需要重新设计的汇总表见 T-D05。

- [ ] 📐 🧑 **T-D04 保留实际播放时长，不只记"是否听完"**（🧑 隐含要求）
  两个数都要能算出来，它们不是一回事：
  - 「播放次数」= `count(*) WHERE counted = 1`（T-D03 写入时已判定）
  - 「总听歌时长」= `sum(played_ms)`，**包括跳过的**

  听 20 秒就切歌，贡献 20 秒给总时长，但不算一次播放。这个区分**必须体现在字段上，事后补不回来**。

- [ ] 📐 🧑 **T-D05 播放历史保留时长，默认永久**（🧑 你的想法③；默认「永久保留」）
  设置项：播放历史保存多久。选项：**永久（默认）** / 5 年 / 2 年 / 1 年。

  **原来这里有个陷阱，已经被 T-D03 的"冻结判定"消掉了。** 之前的方案是清理原始记录后靠"10% 分档直方图"保住阈值可追溯性（11 个计数器，实测 3 年汇总 41,617 个单元格，库从 20.37 MiB 降到 4.70 MiB）。**现在不需要直方图了**——`counted` 在删记录之前就已经算好并写进 `play_stats`（T-D11），清理后统计一条不少。

  实测验证：清理前 `plays=2 / 432 秒`，清理掉 7 条原始记录后 `plays=2 / 432 秒`，完全一致。

  **默认永久保留**的理由：曲库不同步之后，播放历史成了唯一会长大的数据项，但一年也只有 1.12 MiB（gzip）。这个设置是给"我不想留这么多历史"的用户准备的，不是为了省空间。

- [ ] **T-D06 统计口径：不做「只统计本机」开关**
  播放记录参与同步，统计的永远两端合并后的数字。加这个开关会让两台设备显示不同数字，用户会怀疑哪个对。`play_stats` 里本来就有 `device_id`，将来真要加，一个筛选条件就够，不需要现在预留。

- [ ] 📐 🧑 **T-D07 星级评分：独立表 `track_ratings`，同步用新覆盖旧**（🧑 你的想法⑤）
  你说需要评分，所以保留，将来加编辑入口。

  **⚠️ 评分不能挂在 `tracks` 上。** 曲库不同步，两端的 `tracks` 行毫无关系，PC 评 5 星、手机评 3 星永远合并不了。必须单独建表，键是 `fingerprint`（内容算出来的，两端一致）：

  ```sql
  CREATE TABLE track_ratings (
      fingerprint  TEXT NOT NULL UNIQUE,
      rating       INTEGER NOT NULL,      -- 0–5，0 = 未评分
      ...
  );
  ```

  **同步语义：新评分覆盖旧评分**（last-write-wins）。我验证过三种情况都对，包括**清除评分**：

  | 操作 | 结果 |
  | --- | --- |
  | PC 评 3 星（t=200） | 手机同步到 3 星 |
  | 手机改 4 星（t=300） | PC 同步到 4 星 |
  | PC 清除评分（t=400，写 `rating = 0`） | 手机也变成未评分 |

  最后一条是关键：清除评分仍然是一次**带时间戳的写操作**，所以它会正常传播。**不要**实现成"值为空就不参与同步"——那样取消评分永远传不到另一台设备，用户会看到"我明明取消了，手机还是 5 星"。

  **为什么用 0 而不是 `NULL`：** `NULL` 在 `NOT NULL` 下写不进去；改成可空后 `NULL` 和"行不存在"又区分不开——行不存在＝这台设备从没评过，`rating = 0` ＝用户明确取消了，两者必须能分辨。

  **换版本会丢评分。** 评分挂在 `fingerprint` 上，换编码版本就是另一个指纹。这是有意的：`work_key` 适合做听歌次数（版本无关），但评分是"我对这个文件/这个音质的判断"，跨版本继承反而错。

- [ ] 📐 🧑 **T-D08 统计界面与播放历史视图**（🧑 你要求列表 + 日历两种）
  统计页：常听的艺术家/专辑、本周/本月/今年/全部、首次听某首歌的时间、完整听完率。

  **「听的次数最多」做成一项列表**，按次数从高到低排序，**0 次的不参与列表**（`HAVING n > 0`），**未识别文件（`identified = 0`）也不参与**。用户明确删掉了「听的时间最长」这一项，不做。

  总时长、总曲数这两项**包含**未识别文件——它们是真实发生的时间，不是排行榜。

  **播放历史页有两个视图，页面顶部切换：**

  | 视图 | 内容 | 实测耗时 |
  | --- | --- | --- |
  | **列表** | 按 `played_at` 倒序分页，每行显示歌名、艺术家、播放时长、结束方式、来源设备 | 一页 50 条 **0.11 ms** |
  | **日历** | 像日历一样按月铺格子，每格显示当天播放次数（可切换总时长），点某天展开当天记录 | 一个月 **0.55 ms**、一年 **9.4 ms** |

  日历直接查 `play_history` 明细，**不预先分桶存表**：实测按月单独建汇总表（3 年 41456 行）多占 1544 KiB（gzip 441 KiB），而且只有月度粒度，"本周"还得回明细查。

  时间维度能看多远取决于**历史保留策略**：设成 1 年就只看得到一年内，设成永久就都能看。这本来就是"我不想留这么久"的含义，不需要降采样表假装还记得。

  **「听的次数最多」排行里的每一项可以手动删除**（🧑 你要求）。删的是"这条汇总别再出现在我的统计里"，要跨设备生效，所以不能物理删行——本机只有自己那行，对端那 42 次下次同步照样推回来，实测删除等于没做。做法是独立的隐藏标记表 `stats_hidden`（键 `stats_key`），读取走视图 `v_stats`：

  **入口是长按 / 右键 + 二次确认**（🧑 你补充）。行上不挂常驻删除按钮：统计页是给人看的，每行一个垃圾桶会变成批量操作台，也容易误触。长按（Android）/ 右键（Windows）弹上下文菜单 →「从统计中移除」→ 确认框写明「会把这件作品从所有设备的排行里移除，播放历史不受影响」。必须二次确认，因为这个操作**跨设备生效**，本机点了手机上也消失，误触无法靠撤销挽回。

  ```sql
  CREATE TABLE stats_hidden (
      stats_key    TEXT    PRIMARY KEY,
      hidden_at    INTEGER NOT NULL,   -- 用户点删除的时刻
      restored_at  INTEGER,            -- 之后又重新统计的时刻；NULL = 一直隐藏
      updated_at   INTEGER NOT NULL,
      updated_by   TEXT    NOT NULL,
      revision     INTEGER NOT NULL DEFAULT 1
  );
  ```

  两条约束缺一条功能就是坏的：

  1. **`stats_hidden` 必须先于 `play_stats` 合并。** 否则对端那行先到、视图先算了一次，界面会闪一下 50 再跳回 0。合并顺序是协议的一部分。
  2. **必须有 `restored_at` 边界。** 用户删掉 50 次后过两天又听 1 次：只删隐藏行会让旧计数复活成 51，有了边界只算恢复之后的，显示 **1** 次。

  实测四步对账：初始 晴天 50 + 江南 5 = 55 → 删除后只剩江南 5 → 对端行推来仍是 5 → 又听 3 次后 晴天 3 + 江南 5 = 8。清理 `restored_at` 已过的隐藏行与 `updated_at < restored_at` 的旧行是确定性动作，两端各自清理结果一致。

  注意删的是**作品**不是**某一次收听**：同一 `stats_key` 下所有设备的行一起隐藏（用户的意思是"这首歌别再上我的榜"）。要删某一次具体收听，那是播放历史明细页的事，删 `play_history` 里那一行即可，汇总不受影响。

- [ ] **T-D09 性能：先不预计算**
  每天听 3 小时、每首 4 分钟 ≈ 45 条/天，一年 1.6 万条，`GROUP BY` 是毫秒级。**不要过早加物化统计表**——它会引入"缓存和事实不一致"这类最难查的 bug。（`play_stats` 不是物化统计表，它是按设备分行的累加事实，见 T-D11。）

- [ ] 📐 **T-D10 时区：按设备当前本地时区，用 `local_day()` 函数**
  `played_at` 存 UTC 毫秒，查询时才切日/月/年。用户说"本月"想的就是他现在所在地的日历。

  **⚠️ 不能用 `played_at + 固定偏移` 分桶。** 实测（America/New_York）：夏令时切换后偏移从 −5 变 −4，任何写死的常量都会把切换日之后所有凌晨的记录算到前一天——2024-03-11 00:30 与 03-12 00:30 各错位一天。中国没有夏令时，但用户的设备会在别的时区，历史记录也会跟着账号跨时区存在。

  做法：往 SQLite 注册 `local_day(ms)` 标量函数（`deterministic=True`），用系统时区库做真实转换。实测代价：查一个月 **0.55 ms**、一整年 **9.4 ms**、三年全表 4.9 万行 **24 ms**。

- [ ] 📐 **T-D11 听歌汇总表 `play_stats`：主键带 `device_id`**
  **汇总绝不能做成"一首歌一行存总计数 + last-write-wins"。** 实测：PC 听 5 次、手机听 3 次，LWW 覆盖后得到 **3**，正确答案是 8。这和 T-D02 里"计数器列会丢掉另一台的收听"是同一个坑，只不过换了个位置再犯一次。

  正确做法——**主键里带设备 ID，每台设备只写自己那行**：

  ```sql
  CREATE TABLE play_stats (
      stats_key        TEXT    NOT NULL,   -- 已识别 = work_key；未识别 = fingerprint
      identified       INTEGER NOT NULL DEFAULT 1,  -- 0 = 未识别（没标题标签）
      device_id        TEXT    NOT NULL,
      play_count       INTEGER NOT NULL,
      total_played_ms  INTEGER NOT NULL,
      ...
      PRIMARY KEY (stats_key, device_id)
  );
  ```

  这样两台设备**永远不会写到同一行**，同步就是"把对端的行搬过来"，**根本不需要冲突处理**。统计页读的时候 `SUM(play_count)` 就是 8 次。这是本项目里唯一一张不需要合并规则的表。

  附带好处：写入时就累加，所以删掉播放历史明细后汇总不缩水（实测清掉 7 条明细，汇总仍是 10 次 / 2200 秒）。

  **未识别文件的处理（`identified = 0`）：** `stats_key` 退回用曲目 `fingerprint`，**计入总时长和总曲数、不进「听的次数最多」排行榜**。理由：一首没名没姓的歌被听了 12 次是真实发生的时间，不该蒸发；但榜单上出现 `01`、`Track 01` 三次毫无意义。

  **不在标签补上之后回溯合并**，否则就破坏了全项目的「写入时冻结」规则（和 T-D03 的 `counted` 同一条）。补标签后新产生的收听进正常作品键，旧的留在未识别类——数字不倒退、不莫名跳变。

## E. 同步与备份

- [ ] 📐 **T-E01 同步字段**
  `updated_at` / `updated_by` / `revision` / `deleted_at`。`updated_by` 是时钟打平时的确定性裁决者，避免"每次同步结果都不一样"。

- [ ] 📐 **T-E02 同步单位是实体，不是行**
  参与同步的实体（播放列表、**列表条目**、播放记录、星级评分、听歌汇总）逐条合并。曲库不同步（T-E14），所以 `tracks`/`albums`/`artists`/`track_artists` 不在这个讨论范围内。

  **`playlist_items` 原本按"随列表整体替换"设计，已改成逐条同步。** 整体替换做不到两件事：按条目删除无法传播（会复活）、用户无法只拒绝同步进来的某一首歌。代价是多一列 `uid` 和一个墓碑字段。

  **排序键必须用稀疏 `order_key`（间隔 1024），不能用连续 `position`。** 实测在 300 首的列表中间插入一首：连续 `position` 要改动 **298 行**，稀疏 `order_key` 只改 **1 行**。逐条同步下这就是"拖一次歌上传 298 条变更"和"上传 1 条变更"的差别。间隔耗尽时本地重排（500 条 0.45 ms），**重排不得更新 `updated_at`**。

- [ ] 📐 **T-E03 墓碑 `deleted_at`**
  不加则删除永远无法传播：你在 PC 删了列表，同步时手机判定"我这有、你那没有 = 我更新"，推回 PC，**删除被撤销**。

  **只有 `playlist_items` 需要墓碑**（列表条目、`playlists`）。曲库不同步（T-E14），所以 `tracks` 上没有这一列，用户删歌就是物理删除。

- [ ] 🧑 **T-E04 导出导入备份**（🧑 你定的方向）
  v0.3。整库快照存成一个文件，导入时整份覆盖。**先做这个是有意的**：它验证同一套表结构，但不需要解决冲突合并。

- [ ] 🧑 **T-E05 增量备份：每项数据带时间戳**（🧑 你的想法②）
  你的方案：播放统计和播放历史保存每项数据的时间戳，恢复时按时间戳做增量。**每张同步表本来就有 `updated_at`，所以表结构不用改。**

  **你问"数据量会不会太大"——我实测了，不会。** 曲库不同步之后这个数字比原先还小（原来估算里那个 748 KiB 的曲库快照已经不存在了）：

  | 场景 | 大小 |
  | --- | --- |
  | 播放列表 + 设置（几百条），gzip | 几十 KiB |
  | + 1 天播放记录（45 条） | 7.0 KiB 原始 / **约 1.8 KiB 压缩后** |
  | 播放历史 1 年（16000 条），gzip | **1.12 MiB** |
  | 播放历史 10 年 | 十 MB 量级 |
  | 每日增量传输 | **不到 2 KiB** |

  **播放历史是唯一会长大的那一项**，稳态每年约 1 MiB（gzip）。日常增量备份一天只有几 KB，**完全可以每天自动跑**。

  有一个可以省但**不建议现在省**的地方：`uid` 用 36 字符文本，换成 16 字节 BLOB 能省一些（占全库 6%）。省得不多、代码要多写编码转换，**先不做**，记在这里备查。

  ⚠️ **增量恢复的隐藏前提：删除必须靠墓碑传播。** 只拉"比我新的行"是看不到删除的——被删的行不会再被推送。所以 `deleted_at` 本身是一个时间戳，删除也是一次带时间戳的更新，这样增量拉取才能看到它。

- [ ] 📐 🧑 **T-E06 播放列表自动合并，不弹三选一**（🧑 你的想法②；三选项方案已被你自己的墓碑想法取代）
  你最初说冲突时给覆盖 / 不覆盖 / 增量融合三个选项。**加了条目墓碑之后，这个方案被推翻了**——合并变成确定性的，不需要用户裁决用哪一份。

  **合并规则（按 `uid`）：**

  ```
  对端有、本机没有  → 插入
  两边都有          → 按 (updated_at, updated_by) 取大的，整行替换
  ```

  就这两条，**`deleted_at` 只是行里的普通一列，不参与特殊判断**。

  ⚠️ **我最初写错过：把墓碑写成"本机有墓碑、对端没有就保留墓碑"是错的。** 实测场景：t=60 PC 删了 `B`，t=70 手机把 `B` 重新加回列表 → 带那条特殊规则合并结果是 `[]`，**B 丢了**，用户明明加回来的歌另一台永远收不到。原因是那条规则没看对端是否**更晚**，把删除实现成了只能删不能恢复的单向棘轮。

  改成纯 LWW 后，墓碑要支撑的五件事全部仍成立（都实测过）：对端删除传到本机 ✅、本机删除传到对端 ✅、对端新增插入 ✅、拒绝的新增不再出现 ✅、重新勾选能传播 ✅；合并**仍顺序无关且幂等**。

  **普适经验：任何"某列非空就永远保留"的规则都是单向棘轮，先问自己"用户要怎么撤销它"。**

  **实测结果与同步顺序无关**（PC `[A,B,C]` / 手机 `[A,C,D]`，手机上有 `B` 的墓碑）：

  | 同步顺序 | PC 结果 | 手机结果 |
  | --- | --- | --- |
  | PC 先拉 | `[A,B,C,D]` | `[A,C,D]` |
  | 手机先拉 | `[A,B,C,D]` | `[A,C,D]` |

  **顺序无关是取消三选一的前提。** 如果结果取决于谁先同步，就必须让用户裁决；既然结果确定，用户只需要在浮窗里事后微调。

  **条目墓碑解决了原来的"融合会复活删掉的歌"。** 实测：PC `[A,B,C]`、手机删了 `B`，同步后双向都是 `[A,C]`。

  **同名不同 uid 不构成冲突。** 两台设备各建一个「我的最爱」，uid 不同 → 合并后是两个同名列表，这就是"各留一份"，改个名即可。不需要"重名检测"逻辑。

  **设置仍然只有覆盖 / 不覆盖两个选项。** 设置的标识是 `key`，不存在两个同名设置，合并没有意义。判据与播放列表相同：`本地.updated_at > 对端.last_sync_at 且 远端.updated_at > 本地.last_sync_at`，只在真冲突时问，只有一边改过就静默取那一边。

- [ ] 📐 🧑 **T-E07 条目墓碑 + 同步结果浮窗**（🧑 你提的，两件事绑在一起）
  **条目加 `deleted_at`**，让"删掉某首歌"能传播到另一端，也让用户能只拒绝某一条。

  **浮窗：只在确实有变化时弹，只列新增的曲目和被移除的曲目**（不列整个列表——300 首全列出来等于没列表）。每项带勾选框：

  | 类别 | 默认 | 取消勾选的含义 |
  | --- | --- | --- |
  | 新增曲目 | ✅ 加入 | 本机不要这首 → **写墓碑** |
  | 被移除曲目 | ✅ 移除 | 本机保留这首 → **清墓碑** |

  **这两个勾选框必须落成带时间戳的写，不能只"这次跳过"。** 实测对比：

  | 实现方式 | 取消勾选新增的 `D` | 下次同步 |
  | --- | --- | --- |
  | 只是不插入 | PC `[A,B,C]` | ❌ `D` 又出现，每次同步都问一遍 |
  | 写一条墓碑 | PC `[A,B,C]` | ✅ 不再出现 |

  对端那条 `D` 还活着，本机没留下任何记录说"我不要它"——所以**取消勾选就等于删除这一条**，必须和正常删除完全一样。

  反向亦然：重新勾选有墓碑的歌**必须清墓碑**，清墓碑也是一次带时间戳的写。实测 PC 重新勾上 `B` → 同步后手机上 `B` 回来并留住。**这跟评分清除是同一条规则：“没有”也必须是一次显式的、带时间戳的写。**

  **不做「这次都这样」，也不做列表级同步开关**（🧑 你定的）：保持逐条勾选 + 写墓碑这一个机制。理由是它已经能一劳永逸——取消勾选一次，那首歌就不再弹；真要彻底分开，用户该做的是把列表拆开，而不是再加一个容易误触、误触后不知道去哪关的开关。

- [ ] 📐 🧑 **T-E08 同步提示分三级：有变化弹浮窗、无变化弹 Toast、失败弹持久横幅**（🧑 你补的"没变化也要有提示"）
  只做浮窗是不够的——**没变化时也得让用户知道同步跑过了**，否则他点了按钮、界面毫无反应，会以为按钮坏了。但不同结果要用不同强度的提示：

  | 结果 | 形式 | 消失方式 | 理由 |
  | --- | --- | --- | --- |
  | 成功·有变化 | 浮窗（T-E07） | 用户手动关 | 需要决策 |
  | 成功·无变化 | Toast「同步完成，无变化」 | 3 秒自动 | 只是确认收到指令 |
  | 失败 | 顶部持久横幅 + 「重试」 | 重试成功或手动关 | 见下 |

  **失败绝不能用 Toast。** Toast 三秒消失；用户正好低头、切窗口、锁屏，回来看到界面一切正常，实际已经失败——**他会以为数据同步了，但它没有**。

  **Toast 只给手动同步用。** 后台自动同步在无变化时**静默**，只更新 `sync_state.last_sync_at`。一天几十条「同步成功」会让用户迅速学会无视所有提示，连真正的失败也一起忽略掉。自动同步有变化时照常弹浮窗。

  **文案用「同步完成，无变化」而不是「播放列表同步成功」**：①同步的不止播放列表，还有设置、评分、播放历史；②光说"成功"用户会去翻找"到底更新了什么"，翻完发现没变化——"无变化"三个字直接回答了这个问题。

  **不做常驻状态条**（🧑 你定的）：同步是辅助功能，不该占据播放界面的显著位置。要查的时候去设置页。

- [ ] 📐 🧑 **T-E09 同步日志：设置页显示上一次同步的分项报告**（🧑 你要的"显示上一次的日志，失败时给出具体失败项目"）
  Toast 和浮窗都会消失，用户需要一个随时能查的地方。**放在设置里的同步页面，不是主页常驻**。

  页面顶部一行摘要，下面可展开分项：

  ```text
  上次同步：2026-11-23 15:42（手动）· 成功

  设置        ✅ 成功     接收 3 项，发送 1 项
  播放列表    ✅ 成功     接收 2 项，发送 4 项
  评分        ✅ 无变化
  播放历史    ✅ 成功     接收 40 项，发送 12 项
  ```

  失败时对应那行变成「❌ 失败 · HTTP 507 Insufficient Storage」，并保留「重试」按钮。

  **为什么必须精确到分类：** "同步失败"这四个字没法排查。是服务器满了（507）、密码错了（401）、还是某类数据格式不对？分类后用户至少知道去改哪件事。

  **数据结构**（`sync_runs` + `sync_run_items` 两表，不参与同步，只存本机）。`category` 存**人能读的分类**而不是表名——用户不关心 `playlists` 和 `playlist_items` 是两张表，只关心"播放列表同步了吗"。已实测：外键 `ON DELETE CASCADE` 生效、按 `id DESC LIMIT 20` 清理后行数稳定、三个 `CHECK` 约束都真实拦住非法值。一次约 5 行明细、不到 300 字节。

- [ ] 📐 🧑 **T-E10 「清除所有播放列表的墓碑」设置 + 二次确认**（🧑 你要的"抛弃前嫌、重头再来"）
  设置项保留，用途是让用户放掉历史删除记录。**但必须有二次确认窗口**，说明后果。

  **它的破坏性是真实的，实测过：**

  ```
  PC 删了 B → 有 B 的墓碑
  PC 点"清除墓碑" → 墓碑行物理删除，本机不再记得 B 被删过
  与手机同步 → 手机说"我有 B" → B 回来了
  ```

  **数据量上这个设置其实没必要。** 一条墓碑约 90 字节：

  | 场景 | 原始 | gzip |
  | --- | --- | --- |
  | 1 个列表 300 首，无删除 | 27 KiB | 2.6 KiB |
  | + 300 条删除（一年） | 52 KiB | 4.0 KiB |
  | + 3000 条删除（重度折腾） | 279 KiB | 18.5 KiB |
  | 10 个列表各 300 首 + 3000 删除 | 523 KiB | 40.7 KiB |

  带 3000 条墓碑时查"活着的条目" **0.057 ms**，无性能影响。所以这个设置的定位应是**心理上的清理**，UI 描述不该暗示"不清会变慢"。

  **安全水位：加，但单设备时不设限。** 有对端设备时只清 `deleted_at < min(所有设备 last_sync_at)` 的墓碑（实测这样清完再同步，被删的 B 不会回来）；没有任何对端设备时直接全清——本来就不存在"对端有 B"的情况，全清是安全的，而且用户点按钮看到"清了 0 条"只会以为功能坏了。二次确认和逻辑正确是两件事，两个都要。

- [ ] 📐 **T-E11 墓碑自动回收**
  `deleted_at` 早于 90 天、且所有已知设备都已同步过该时间点的墓碑，物理删除。不需要用户干预，和 T-E10 的手动按钮是两回事。读 `devices.last_sync_at`。

- [ ] **T-E12 WebDAV 双向同步**
  v0.6。复杂度最高，等两端都稳定后再做。

- [ ] **T-E13 同步冲突的其他已知局限**
  - 靠系统时钟。手机时钟被调快 5 分钟，它在冲突里就永远赢。更严谨的方案是 HLC（混合逻辑时钟），现在不做，但 `updated_at` 单独列出来就是为了将来原地替换。
  - 顺序无关只在合并逻辑正确时成立。实测已验证播放列表的合并与同步顺序无关，但**这个性质要靠测试守住**——一旦有人在合并里加入"本地优先"之类的例外，顺序无关就没了，而故障表现只是"偶尔多一首或少一首"，很难排查。
  - `play_stats` 是唯一的例外：它根本不需要合并规则，因为两台的 `device_id` 不同，永远写不到同一行。

- [ ] 📐 🧑 **T-E14 曲库不同步**（🧑 你的决定："我们不同步曲库信息，只同步设置、听歌汇总、播放列表、播放历史"）
  `artists` / `albums` / `tracks` / `track_files` / `track_artists` 全部退化为**本机私有的扫描缓存**：去掉 `uid`、去掉 `updated_at`/`updated_by`/`revision`/`deleted_at`。用户删歌就是 `DELETE` 行，不需要墓碑。

  **⚠️ 这不是为了省流量，那个理由是错的。** 实测曲库 10000 首全量 JSON 2.36 MiB、gzip 后 **0.79 MiB**；而播放历史一年的量（16000 条）gzip 后是 **1.12 MiB**，比整个曲库还大。真要省流量该省的是播放历史。

  真正的三条理由，都是"同步了反而更糟"：

  1. **文件物理位置无法同步。** PC 的 `D:/Music/x.mp3` 在手机上不存在，同步来的 8000 条记录在手机上全是"有记录、无文件"的灰条，纯噪音。
  2. **两端扫描结果互相覆盖。** 手机扫出 3000 首、PC 扫出 8000 首，合并后手机要显示 5000 首"缺失"，每次同步都要面对这个数字。
  3. **"用户主动删除"的语义崩坏。** PC 删歌同步过去手机也标删除，但手机端本来就没这个文件；反过来手机扫不到某文件，同步到 PC 会让 PC 以为歌丢了。

  **那两端靠什么对齐？靠两个函数，不是靠数据。** `fingerprint`（内容算出的文件身份）和 `work_key`（标签算出的作品身份）都是纯函数，两端各算各的，结果一定一致。所以曲库表怎么删怎么重建都不影响对端——它是缓存，不是真源。

  连带改动：`play_history.track_uid` → `track_fingerprint`（两端 uid 毫无关系）；`rating` 从 `tracks` 挪到独立表 `track_ratings`（T-D07）；`playlist_items.ref_uid` 删掉（跨设备无用），只留 `ref_fingerprint`。

## F. 智能播放列表（**实现推后到 v0.5+**）

> **整个 F 区的设计保留，但实现排在最后。** 产品上不追求这个功能，先按"能听 → 好听"走完 v0.1–v0.3。保留设计的两个理由：①表结构已经为它准备好了（`playlists.kind` + `smart_query` 两列），现在删掉将来加回来还要改表；②它是数据模型的测压点——`play_stats` 的跨设备聚合、`track_ratings` 的 JOIN、`work_key` 的统计口径、`is_missing` 的反向映射，全都是因为要让智能列表查得对才被逼着设计对的。

- [ ] 📐 **T-F01 条件存 JSON 语法树，不存 SQL，不发明 DSL**
  三种逻辑节点 `{"all":[…]}` / `{"any":[…]}` / `{"not":{…}}` 可嵌套，叶子是 `{field, op, value}`。

  **不用 SQL 片段**：最坏情况是**你从论坛下载一个别人分享的播放列表，等于在那台机器上执行远程代码**，它能读整个数据库。

  **不发明文本 DSL**（`artist:"周杰伦" AND year:>2000`）：要写词法分析器 + 语法分析器 + 错误提示，而用户实际是从下拉菜单选「艺术家 等于 周杰伦」，**没人手打那行查询**。

- [ ] 📐 **T-F02 白名单编译器**
  安全性来自**编译方式**，不来自输入校验：

  ```
  field → 查白名单，得到固定 SQL 列名    用户字符串不进 SQL
  op    → 查该字段允许的算子表，得到硬编码片段
  value → 永远作为 ? 绑定参数            从不拼接
  ```

  原型验证四种注入全部被挡：

  | 攻击 | 结果 |
  | --- | --- |
  | 值填 `Rock'; DROP TABLE tracks; --` | 安全编译，0 结果，表完好 |
  | 字段名填 `genre; DROP TABLE tracks` | 拒绝：未知字段 |
  | 算子名填 `is; DROP TABLE tracks` | 拒绝：不允许的算子 |
  | 搜 `50%` | 转义后只命中真正含百分号的，不乱匹配 |

  限制：嵌套 ≤ 8 层、叶子 ≤ 64 个。

  **这个编译器本身不难：原型 130 行就写完了。** 真正的成本在编辑条件的那套 UI（下拉联动、算子随字段类型变、条件行增删、嵌套分组拖拽），那是界面工作不是算法难度。

- [ ] **T-F03 `LIKE` 通配符转义**
  `%` 和 `_` 是通配符。搜「50%」不转义会匹配所有含 50 的歌。必须 `LIKE ? ESCAPE '\'`。

- [ ] **T-F04 编辑 UI**
  条件行的增删、拖拽排序、嵌套分组。因为存的是 JSON 数组，增删就是数组 push/remove，**不需要解析和重新格式化文本**——这是不存 SQL 字符串的另一个好处。

- [ ] **T-F05 版本兼容**
  JSON 带 `"version": 1`。遇到不认识的字段，把整个智能列表标为「需要更新版本」并置为不可用，**不能静默忽略那一条条件**——否则列表内容和名字不符（"90 天没听过"的列表里出现昨天刚听的歌），比不可用更糟。

- [ ] 📐 **T-F06 结果不设上限，全部显示**
  查询不加 `LIMIT`，命中多少显示多少；列表按需游标分页（一次 100 行），只取 id / 标题 / 艺术家 / 时长，其余字段点开再查。

  实测 20 万首全命中：取全字段 176 ms / 18.3 MiB，只取 id 45 ms / 3.1 MiB；5 万首 2.4 MiB / 16 ms。跳过 2 万行再取 100 行 4.7 ms。

  排序必须追加 `, t.id ASC` 兜底 —— 否则「按添加时间」「按标题」遇到重复值时分页会漏行或重行。

- [ ] 📐 **T-F07 时间算子必须是 `within_days` 和 `before_days` 两个**
  **不能用 `NOT before_days` 代替 `within_days`**，`NULL` 三值逻辑会让「从没听过」混进「最近听过」。实测（A 在 1000 听过、B 在 5000 听过、C 从没听过即 `last_played IS NULL`；现在 6000，问「最近 2 天内听过」）：

  | 编译形式 | 结果 |
  | --- | --- |
  | `before_days` → `col IS NOT NULL AND col < 4000` | `['A']` ✓（2 天**之前**听过＝很久没听） |
  | `NOT (上面那条)` | `['B', 'C']` ✗ **从没听过的 C 混进了"最近听过"** |
  | `within_days` → `col IS NOT NULL AND col >= 4000` | `['B']` ✓ |

  两类需求都是最常用的：「最近 7 天我听的新歌」（`within_days`）和「90 天没听了，帮我重新发现」（`before_days`）。原白名单里的 `after_days` / `before` / `after` 已删除——前者方向重复，后两者要求用户填绝对时间戳、界面上没法输入。`added_at` 配 `within_days` / `before_days` 之后，「最近 30 天加入的歌」才能表达。

- [ ] 📐 **T-F08 `is_missing` 的反向映射必须集中在一处并有单测**
  `is_missing` 编译成 `(t.has_local_file = 0)`，所以 `value = true` 要绑 `1`。原型第一次写成了 `0 if val else 1`，跑出来「缺失=true」返回 4 首、「缺失=false」返回 1 首，**正好颠倒**。知道设计意图的人第一次都会写反，必须有单测覆盖两个方向。

- [ ] 📐 **T-G03 不建表**
  每次从文件读。十万首歌词存库是几百 MB 纯冗余，还要处理"文件换了这个库没换"的失效问题。歌词跟着文件走。

- [ ] 📐 🧑 **T-G04 `.lrc` 编码探测：五级回退**（🧑 你圈出来的坑；顺序已确认）
  `.lrc` **没有统一编码**。日文歌常见 Shift-JIS，中文老歌常见 GBK/GB18030，现代多为 UTF-8（可能带 BOM）。直接按 UTF-8 硬读，**一半的中文老歌词会变乱码**。

  按顺序探测，**第一个严格通过的就采用**：

  ```
  1. BOM        有 BOM 就直接采信（UTF-8 / UTF-16LE / UTF-16BE）
  2. UTF-8      严格校验，遇到非法字节序列立刻失败
  3. GB18030    中文老歌词的主场；它是 GBK 的超集，能覆盖两者
  4. Shift-JIS  日文歌词
  5. Latin-1    兜底，永不失败（任何字节都是合法 Latin-1）
  ```

  **为什么 GB18030 排在 Shift-JIS 前面：** 两者都是多字节编码，会互相误判。但 GB18030 的字节结构约束更严，误判率低；而且中文老歌词的数量远多于日文。排错了的后果是"中文歌显示成日文乱码"，比反过来更容易被用户察觉并反馈。

  **Latin-1 放最后的意义是"必须有个确定结果"。** 探测链不能有"无法识别"这个分支——那意味着歌词空白。宁可显示乱码也让用户看到内容，因为乱码至少能判断"这个文件编码不对"，空白什么信息都没有。

- [ ] **T-G05 内嵌歌词的多种标签**
  ID3v2 的 `USLT` / `SYLT`，FLAC 的 `LYRICS`，MP4 的 `©lyr`，以及 `TXXX:LYRICS` 这类非标准标签。TagLib 不统一处理，得逐个试。

- [ ] 📐 **T-G06 歌词展示形态：全屏页 + 桌面悬浮窗**
  **全屏歌词页**：点封面进入，大字居中，当前行高亮。Windows 和 Android 共用一套。
  **桌面悬浮窗**（Windows 可选开关）：置顶、半透明、鼠标穿透可切换。桌面播放器的刚需，手机没有。
  **不做侧栏**：窄屏挤，宽屏又不如全屏，少一个要维护的布局。

- [x] **T-H01 UI 技术选型：两端各用各的原生栈**（🧑 你定的方案 B）
  **Windows = Qt 6 Quick / QML；Android = Kotlin + Jetpack Compose + Material 3。Core 层一份共用。**
  为什么不是"一套 QML 跑两端"：Qt for Android 的体积是决定性因素——Qt Quick 最小 hello world 的 APK 约 27 MB、常规 App 装完约 92 MB，而 Kotlin + Compose 约 12–18 MB，**差 5–8 倍**。另外 Android 的媒体生态（通知栏、锁屏、蓝牙按键、耳机拔出、Android Auto）用 Qt 要自己写 Java 层，用 Media3 几乎白送。
  代价写在明处：**要维护两套 UI 的一致性**（配色、间距、动效、文案、空状态）。缓解靠一份集中的设计规格 + "功能边界两端一致，不允许某功能只有一个端有"，详见 [ARCHITECTURE.md](ARCHITECTURE.md) §9。
  完整依赖清单与许可证矩阵见 [DEPENDENCIES.md](DEPENDENCIES.md)。

- [ ] 📐 **T-H02 双队列 + 插播颜色区分**（🧑 你补充的）
  `play_queue.origin` 记录来源，UI 直接读这个值决定颜色，**不需要猜**某条是不是插播：

  | 值 | 谁写进去的 | 具体场景 | 播完之后 |
  | --- | --- | --- | --- |
  | `user` | 用户显式操作 | 点「添加到队列」、拖专辑进队列、拖动排序后的行 | 留着 |
  | `play_next` | 用户点「下一首播放」 | 正听 A，想让 B 紧跟着播，又不打乱后面 | **用完即弃** |
  | `context` | 系统自动续 | 双击专辑第 3 首，系统按原序补整个专辑 | 换上下文时整批撤掉 |
  | `shuffle` | 系统生成 | 同一上下文开了随机，顺序由洗牌算法生成 | 播完一轮触发重洗 |

  **`user` 与 `context` 的区别是"谁决定的顺序"**：双击专辑第 3 首时后面是系统按原序补的（`context`）；用户把第 7 首拖到第 4 位，那行变成 `user`。
  **`play_next` 必须单独记**：它要"插入当前播放行紧后面"而不是追加到末尾，且播完就删。
  **`shuffle` 记的是"这行顺序来自洗牌结果"**：关掉随机后重新变回 `context`（或被手动调过则 `user`）；洗牌顺序就存在队列行的 `position` 里，不需要额外的表。

  **数据层记四种，视觉层只高亮一种。** 成本只是一列文本；但**界面上只给 `play_next` 上色**。四种都上色用户要记四套规则，日常又看不出区别。只记一条：高亮的那条是插播，播完就没了。数据层的四种留给将来用（"清空队列"时用户排的需确认、系统补的可直接丢）。

- [ ] 📐 **T-H03 持久化洗牌顺序**
  洗牌是**生成一次随机顺序并保存**，不是"每次随机取一首"。后者会导致同一首歌短时间内重复出现，而且"上一首"回不到真正的上一首。
  **重新洗牌的时机，三层：**

  | 时机 | 行为 |
  | --- | --- |
  | 首次对某列表开启随机 | 生成一次顺序并保存 |
  | 播完一轮 | 自动重洗，但**避开刚播完那首**（否则下一轮第一首又是它） |
  | 手动「重新洗牌」按钮 | 立即重来 |

  **不做"切换列表时重洗"**：切出去再切回来顺序全变了，用户会懵——"我刚听到第 5 首，怎么变成第 12 首了"。

- [x] **T-H16 视觉规格：统一设计语言、底部导航、动态取色默认关**（🧑 你定的三条）
  2026-11-25 定案，是 UI 层的宪法，写界面前先回来对一次。完整论证见 [ARCHITECTURE.md](ARCHITECTURE.md) §9。
  **① 统一设计语言（方案 A）**：两端是同一个 App，不是"各自像本地应用"。Android 用 Material 3、Windows 用 Qt Quick 的 Material 风格向**同一份规格**对齐，不用 Fluent。理由：同产品同用户同数据 + 一个人维护，两套规格迟早分叉，后续返工比一开始就统一贵。代价是有意接受的——Windows 用户会觉得"不太像 Windows 程序"。唯一允许的平台差异是**交互惯例**（右键 vs 长按）与**窗口形态**（桌面多列/侧栏，手机单列），视觉语言必须一致。
  **为什么不走"Windows 用 Fluent"**：Qt 6.8 起的 FluentWinUI3 风格仍在开发中，`StackView`/`SplitView`/`Drawer`/`SwipeView`/`TreeViewDelegate` 等**明确未支持、会回落 Fusion**（[Qt 文档](https://doc.qt.io/qt-6/qtquickcontrols-fluentwinui3.html)），而播放器必然要用前两个。那不是"WinUI3 风格的应用"，是"一半 WinUI3 一半 Fusion"的拼接界面。
  **①-b 两条对 Windows 的让步**：a) 用 Material **Dense 变体**（`QT_QUICK_CONTROLS_MATERIAL_VARIANT=Dense`，Qt 官方建议桌面用 Dense）——同一套语言，密度按输入设备调（手机 48dp / 桌面 32dp 级）；b) **标题栏与窗口边框走原生**（Mica / 自定义标题栏），不纳入"视觉规格必须一致"的范围，因为它属于操作系统容器而非应用内视觉。
  **② 导航**：手机用 Material 3 `NavigationBar`（四个入口：库/播放/搜索/设置，80dp），桌面改成左侧常驻侧栏，**信息架构相同、容器不同**，换设备不用重学。
  **③ 动态取色（Material You）默认关闭**：主色随壁纸变不可接受（品牌色 + 专辑封面本身又是配色源）。设置项 `ui.dynamic_color`，`device` 作用域（壁纸是设备相关的）。开启后动态取色覆盖主色，但**强调色与语义色仍由我们控制**，避免"危险按钮变成绿色"。

  两次构建二选一，**不能同进程混用**（符号冲突、全局状态冲突）：CMake 用 `MP3_FFMPEG_ROOT` 切换，major 版本必须对齐。开发阶段先装 MSYS2 的 `mingw-w64-ucrt-x86_64-ffmpeg`，等 v0.1 出声后再自编译音频专用版（`--disable-everything --disable-gpl --disable-network --disable-encoders --disable-video --enable-small` + 音频解码器白名单）做 A/B 比对。Android 侧交叉编译留到 v0.4。

## 优先级建议

按"用户能感知到的价值 ÷ 实现成本"排：

| 优先级 | 项 | 理由 |
| --- | --- | --- |
| 高 | T-D03 播放次数阈值 | 数据已经都在，只是加一个设置项和一条查询 |
| 高 | T-E04 导出导入备份 | 是 WebDAV 同步的前置验证，也防止用户数据丢失 |
| 高 | T-D05 历史保留时长 | 实现成本低，和阈值一起做 |
| 中 | T-F 智能播放列表 | 依赖曲库成熟，曲库太小时感受不到价值 |
| 中 | T-G 歌词 | 依赖解码器和 UI 都稳定 |
| 低 | T-E12 WebDAV 同步 | 复杂度最高，要两端都稳定后才有意义 |

前提：**先有能用的播放功能和像样的曲库管理**。上面全部建立在"能正常听歌、曲库信息准确"之上。
