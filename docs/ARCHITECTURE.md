# 架构设计

MusicPlayer3 的分层、线程模型与各项取舍的理由。

## 1. 分层

两端共用一份 Core，UI 层各用各的原生技术栈（理由见 §9）。

```text
┌───────────────────────────┐   ┌───────────────────────────┐
│  Windows UI 层             │   │  Android UI 层             │
│  QML + Qt Quick Controls  │   │  Kotlin + Jetpack Compose │
│  D3D11 / D3D12 / Vulkan   │   │  GLES / Vulkan            │
└─────────────┬─────────────┘   └─────────────┬─────────────┘
              │ 属性绑定 / 信号               │ Compose 状态
┌─────────────┴─────────────┐   ┌─────────────┴─────────────┐
│  Windows App 层            │   │  Android App 层            │
│  Qt 壳：QML 引擎宿主、      │   │  Activity + Service、      │
│  C++ 模型暴露、文件对话框   │   │  Media3 会话、SAF、JNI 桥   │
└─────────────┬─────────────┘   └─────────────┬─────────────┘
              │ 普通 C++ 调用                 │ 普通 C++ 调用（经薄 C 包装）
┌─────────────┴───────────────────────────────┴─────────────┐
│  Core 层    纯 C++20 静态库，零 Qt 依赖、零平台假设          │
│  解码 · 混音 · 重采样 · DSP · 输出 · 元数据 · 媒体库 · 扫描  │
│  职责：全部实质性逻辑。两端同一份源码。                     │
└───────────────────────────────────────────────────────────┘
```

UI 层各自包含：像素、手势、动画、平台惯例。不含任何播放逻辑。

### 为什么 Core 层不能依赖 Qt

三个具体好处，不是教条：

1. **可以独立测试。** 播放引擎的问题（seek 精度、gapless 边界、EQ 相位）不需要启动图形界面就能复现。Core 的测试是普通可执行文件，在无 GPU、无声卡的机器上也能跑。
2. **编译快、依赖小。** 改一行 DSP 代码不必重新编译 Qt 的 moc 产物。
3. **未来可选路径。** 命令行工具、无头音乐服务器、其他 UI 框架的移植，都只需要 Core。

### 为什么 UI 层不做播放逻辑

QML 的 JavaScript 引擎在 GC 时可能停顿几十毫秒，而音频线程的预算是个位数毫秒。任何"在 QML 里 push 一段音频"的设计都会在负载下爆音。UI 只读状态、只发命令。

## 2. 线程模型：设备即时钟

这是全篇最重要的一个决定。

### 常见错误做法

大多数播放器这样组织：解码器以自己的速度产出 PCM，写入一个环形缓冲区；声卡以另一个速度拉取。两者频率不可能完全相等（晶振有 ppm 级偏差），于是缓冲区要么慢慢填满、要么慢慢排空。解决办法是"漂移校正"：检测缓冲水位，插入或丢弃采样，或微调重采样率。这套机制能工作，但调试极其痛苦——它把两个独立时钟的相位差，变成了一个需要持续调节的反馈回路。

### 本项目的做法

**声卡回调就是主时钟。** 设备每次需要 N 帧，就直接在回调里从环形缓冲区取 N 帧；取不到就写静音并记一次 underrun。没有第二个时钟，也就没有任何需要同步的东西。

```text
   ┌──────────────┐   解码    ┌──────────────┐   取帧    ┌──────────────┐
   │ 解码线程      │ ────────▶ │ 环形缓冲区    │ ────────▶ │ 声卡回调线程  │
   │ (预读 1–2 s) │  写入     │ (无锁 SPSC)  │  读取     │ (实时优先级)  │
   └──────────────┘           └──────────────┘           └──────────────┘
```

- 解码线程平时跑到缓冲区满，然后等待。
- 缓冲区水位低于阈值（约 0.5 s）时唤醒解码线程。
- 声卡回调只做：读环形缓冲区 → 过 DSP（EQ、音量）→ 写入设备缓冲。全部是定长、无分配、无锁的操作。
- 解码慢于实时（网络文件、慢速存储、极重的 DSP）时，症状是**一次可听见的 underrun**，而不是音调逐渐变调。前者可诊断，后者不可。

### 由此获得的性质

- **seek 不必停流。** 清空环形缓冲区，解码线程从新位置重新填充，声卡继续按自己的节奏拉取——中间插入的静音长度等于重新填充的时间。
- **gapless 很自然。** 环形缓冲区里先写入当前曲目的尾部，紧接着写入下一曲的开头，声卡根本不知道有换曲发生。
- **交叉淡化同理。** 混音发生在写入环形缓冲区的时候，两首歌的重叠段在解码线程侧就混合好。

## 3. 时间单位：帧

引擎内部所有位置、长度、时长都用 `FrameCount`（`int64_t` 帧数），不用 `double` 秒。原因：

- 帧数是精确的整数，累加不产生误差；`double` 秒在 48 kHz 下累加一小时会有可测量的偏差。
- 换算成秒是一次除法（`frames_to_seconds()`），换算成纳秒也是（`frames_to_ns()`），不丢信息。
- 比较"是否播到结尾"用整数相等即可，不需要 epsilon。

`double` 秒只在两个地方出现：文件里读到的时长（FFmpeg 给的就是 double），以及 UI 显示。转换集中在少数几个函数里。

## 4. 音频格式

`AudioFormat` 描述三件事：采样率、声道布局、采样格式。

- **采样格式**区分交错（`S16`/`S32`/`F32`）和平面（`S16P`/`S32P`/`F32P`）。FFmpeg 的 SIMD 路径大量使用平面格式，DSP 链路保持平面可以省掉很多解交错。
- **声道布局**是一个枚举而不是裸整数，这样"5.1 有 6 个声道"这个知识只存在于一处（`channel_count()`），不会散落在各处。
- **管线内部统一用 F32**。解码器输出 F32，DSP 全是 F32，只在最后写设备缓冲时按设备要求转换。整数域的中间运算会产生量化噪声累积，浮点不会。

## 5. 错误处理

实时音频线程里不能抛异常（栈展开的时机和耗时不符实时约束），所以 Core 全部用返回值表达错误：

```cpp
struct Status {
    ErrorCode code = ErrorCode::Ok;
    std::string message;   // 仅用于诊断，不是给用户看的文案
    explicit operator bool() const { return code == ErrorCode::Ok; }
};
```

- 返回值成功/失败用 `Status`，不用异常。
- `message` 是给开发者看的英文诊断文本；面向用户的本地化文案由 App 层根据 `ErrorCode` 生成。
- 实时线程内的失败路径必须无分配——因此那里用的 `Status` 消息要么是空串，要么来自静态字符串。详细规则见各接口头文件的注释。

## 6. 依赖与可选性

| 依赖 | 用途 | 缺失时 |
| --- | --- | --- |
| FFmpeg (libavformat/codec/util/swresample) | 解码与重采样 | 解码器报告 `NotSupported` |
| miniaudio（单头文件，vendor 进仓库） | 设备封装 | — |
| TagLib | 元数据与封面 | 元数据为空，仍可播放 |
| SQLite | 媒体库 | 库功能不可用，仍可播放文件 |
| Qt 6 Quick | Windows 端 UI | App 层不构建 |

可选项的完整清单（含许可证与"为什么是它"）在 [DEPENDENCIES.md](DEPENDENCIES.md)。

约束：**Core 层在缺少任何一个可选依赖时都必须能编译通过。** 这让仓库在任何一台装了编译器的机器上都能 `cmake -B build` 成功，也让 CI 不必先装 1.5 GB 的依赖。

同一条约束的第二种用法：**所有第三方库只能出现在 `core/src/` 的某个 `.cpp` 里**，`core/include/mp3/` 下面不许 `#include <libavcodec/...>`。这样换库时改动范围是可预期的。

## 7. 平台差异

| 事项 | Windows | Android |
| --- | --- | --- |
| 音频输出 | WASAPI（共享/独占/位精确） | AAudio（8.0+），OpenSL ES 兜底 |
| 位精确可达性 | 独占模式可做到（WASAPI exclusive） | 基本不可达：仅 Android 14+ 部分 USB DAC 支持 `MIXER_BEHAVIOR_BIT_PERFECT`，且为可选设备特性 |
| 缓冲大小 | 可低至 64 帧 | 通常 192–960 帧，由系统决定 |
| 采样率切换 | 重开流，断点至多几十毫秒 | 同；但 `Shared` 模式下 AAudio 走系统混音，通常固定 48 kHz |
| 后台播放 | 窗口关闭即退出（可配置） | 必须前台服务 + 通知（Java 侧 `extends Service`） |
| 文件访问 | 任意路径 | SAF（`content://` URI）或授权目录 |
| 曲库扫描 | 直接 `stat()` 枚举目录 | 走 SAF 树枚举（`DocumentFile`），拿不到真实路径、拿不到 `stat` 时间戳 |
| 元数据来源 | 文件本身 | 文件本身；MediaStore 可作补充 |

`AudioOutput` 接口将这些差异封装在两个实现后面；`Decoder` 在 Android 上需要通过文件描述符打开（`content://` URI 先由 App 层解析成 fd），这是它唯一需要平台适配的地方。

扫描差异值得单独说一句：Windows 上 `track_files` 的增量判据（`size` + `mtime` + `fp_verified_at`，见 DATA_MODEL §2.5）在 Android 上**拿不到 mtime**，SAF 只给 `lastModified`（毫秒精度、可能为 0）。所以扫描器需要一个"平台能力"抽象：能力齐全时走增量，缺 mtime 时退化成"每次都读头尾算指纹"。这是实现细节，不影响数据模型——表结构两种平台共用，只是填充质量不同。

## 9. 两端各用各的 UI 框架

**结论：UI 层分成两套技术栈——Windows 用 Qt 6 Quick + QML，Android 用 Kotlin + Jetpack Compose。Core 层一份共用，一行不改。** 三层分层的骨架保留，变的是 UI 层的实现数量和 App 层要写两份。

### 为什么可以分开，以及当初那个决定为什么值钱

Core 层是纯 C++20 静态库，零 Qt 依赖、零平台假设。它只知道两件事：怎么把文件变成 PCM（`Decoder`），怎么把 PCM 交给设备（`AudioOutput`）。这两个接口在 Windows 和 Android 上的实现不同，但**契约相同**——`OutputMode` 三档的语义（`Shared`/`Exclusive`/`BitPerfect`）两端一致，只是 Android 上 `BitPerfect` 大概率协商失败并返回错误。

这就是为什么换掉 Android 的 UI 框架不需要动引擎：UI 框架从来没被 Core 看见过。当初"Core 不许 `#include` Qt"不是洁癖，它换来的是**今天这个选择是免费可逆的**——将来若再改主意，只重写 App + UI，引擎与数据层保值。

### 分成两套的代价，说清楚

| | Windows | Android |
| --- | --- | --- |
| UI 技术栈 | Qt 6 Quick（QML + C++ 绑定） | Kotlin + Compose + Material 3 |
| 与 Core 的接口 | 直接 C++ 调用，QML 属性绑定 | JNI（App 层写桥，Core 侧只是一层薄 C 包装） |
| 媒体生态 | 自己管（窗口、任务栏缩略图、媒体键） | **Media3 接管**通知栏、锁屏、蓝牙按键 |
| 构建 | CMake + MinGW/MSVC + `windeployqt` | Gradle + AGP + NDK（交叉编译 Core） |

**真正的代价不是写两遍代码，而是维护两遍一致性。** 以后每加一个功能，用户会期待两端像同一个产品：配色、间距、动效曲线、文案、空状态。两套 UI 意味着两套设计系统，且必须在**同一份设计规格**上派生——否则半年后它们会变成两个长得不像的 App。这不是代码问题，纪律问题。

配套约束（写在这里是为了以后有据可依）：

- **设计规格先于实现**：配色、圆角、间距、字号、动效时长集中在一份文档里，两端只做"翻译"不做"发挥"。
- **功能边界两端一致**：不允许出现"这个功能只有 Android 有"。允许平台特有交互（如 Windows 的右键菜单），但不允许功能缺失。
- **Core 的能力只暴露一次**：JNI 桥和 QML 绑定都是对同一组 Core 接口的包装，不因为"Android 好写"就多开一个 Core 入口。

### 为什么这样分反而更省

因为**两端各自最贵的东西不一样**，而分开后各拿各的：

- **Android 最贵的是媒体生态**（前台服务、MediaSession、锁屏、蓝牙、耳机拔出、车机）。用 Media3 的 `SimpleBasePlayer` 转发到我们的 C++ 引擎，这些几乎白送；用 Qt 则全部要自己写 Java 层，且 Qt 在 Android 的媒体集成并不比自己写省。
- **Windows 最贵的是桌面集成**（高 DPI、多显示器、窗口拖放、任务栏、媒体键、输入法）。Qt 把这些做完了。
- **体积**：Android 原生 12–18 MB，Qt for Android 最小包 27 MB、装完约 100 MB。见 [DEPENDENCIES.md](DEPENDENCIES.md) §6。

### 明确不变的

- Core 层一行代码都不用为这个改动改。
- 数据模型（DATA_MODEL）里所有表两端共用；曲库本就不同步（DATA_MODEL §0.1），不存在"手机库和电脑库打架"。
- 同步协议、播放统计口径、`work_key` 聚合规则，全部与平台无关。

### 一个必须承认的风险

**一个人维护两套 UI 是项目烂尾的经典姿势。** 缓解手段只有三条，缺一条这个决定就站不住：

1. Core 与数据层绝对不写两份（这是底线，也是唯一真正不可妥协的）。
2. 设计规格集中一份，避免"两套 UI 各自演化"。
3. **Windows 端晚一点做、但功能上不残**——它不是"能跑就行"的副产物，只是排期在后。

### 视觉规格：统一设计语言，两端同一份（已定案）

三条设计决策已经定了，写在这里当作 UI 层的宪法，后面写任何界面前先回来对一次：

**① 统一设计语言（方案 A）：两端是同一个 App，不是两个各自像本地应用的软件。**

- Android 用 Material 3（`androidx.compose.material3`，官方参考实现），Windows 用 Qt Quick 的 Material 风格**向同一份规格对齐**，而不是改用 Fluent。
- 理由：同一个产品、同一批用户、同一套数据，且只有一个人维护——两套设计规格迟早分叉，而分叉后的返工比一开始就统一贵得多。
- 代价：Windows 用户会觉得"这不像 Windows 程序"。**这是有意接受的取舍**，因为"看起来是同一个产品"对我们更重要。
- **为什么不走"Windows 用 Fluent"这条路**（这是当时真正对比过的方案，记下来免得以后又想改）：Qt 6.8 起确实有官方的 FluentWinUI3 风格（`import QtQuick.Controls.FluentWinUI3`，跟 WinUI 3 与系统主题色走），但它**至今仍在开发中且明确列了未支持的控件**——`Dial`、`Drawer`、`HorizontalHeaderView`、`SplitView`、`StackView`、`SwipeDelegate`、`SwipeView`、`TreeViewDelegate`、`Tumbler`、`VerticalHeaderView`，遇到这些会回落到 Fusion 风格（见 [Qt 文档](https://doc.qt.io/qt-6/qtquickcontrols-fluentwinui3.html)）。而播放器**必然**要用 `StackView`（页面栈）和 `SplitView`（导航 + 内容分栏）——正好都在名单里。结果不会是"一个 WinUI3 风格的应用"，而是"一半 WinUI3 一半 Fusion"的拼接界面，比统一 Material 更难看也更难调。**B 省下的是"设计规格写两份"的活，换回来的是"跟一个不完整的 Qt 风格搏斗"的活。**
- 唯一允许的平台差异：**交互惯例**（Windows 右键菜单、Android 长按菜单）与**窗口形态**（桌面可多列/常驻侧栏，手机必须单列+底部导航）。视觉语言（配色、圆角、间距、字号、动效时长）必须一致。

**①-b 两条对 Windows 的明确让步**（把"统一"的边界划清楚，避免以后为每个控件争论一次）：

1. **Windows 用 Material 的 Dense 变体**（`QT_QUICK_CONTROLS_MATERIAL_VARIANT=Dense`）。Qt 官方明确建议桌面平台用 Dense，控件与字体都更小（见 [Material Style 文档](https://doc.qt.io/qt-6/qtquickcontrols-material.html)）。这不破坏统一性——**同一套设计语言，密度按输入设备调**：手机是手指（48dp 触摸目标），桌面是鼠标（32dp 级）。
2. **Windows 的标题栏与窗口边框走原生**（Windows 11 的 Mica / 自定义标题栏），**不纳入"视觉规格必须一致"的范围**。理由是这一块属于"操作系统容器"而不是"应用内视觉"——它由系统绘制、跟随系统主题，强行统一反而更怪。两边本来也都要自己写（Qt 没有免费的 Mica 标题栏）。

补上这两条之后，A 与 B 在 Windows 上的实际差距只剩"控件是圆角矩形还是 WinUI 的胶囊形"——为这一个差异维护两份设计规格，不值。

**② 导航：手机用底部导航栏，桌面用左侧常驻侧栏。**

- Android：Material 3 的 `NavigationBar`，四个入口——库 / 播放 / 搜索 / 设置。占 80dp 高度，对"边听歌边浏览"是划算的。
- Windows：同四个入口，改成左侧常驻侧栏（宽屏下底部导航是浪费横向空间）。
- **两端的信息架构相同**，只是容器不同。这样用户换设备不用重新学。

**③ 动态取色（Material You）：默认关闭，设置里可选。**

- Android 13+ 支持 `dynamicColor`，从壁纸取色自动生成配色方案。它确实好用，但对播放器有个具体问题：**主色会随用户壁纸变**，而我们想用品牌色，且专辑封面本身又是另一套配色源。
- 所以默认关、走我们自己的配色方案；设置里给开关（`ui.dynamic_color`，`device` 作用域——壁纸是设备相关的）。开启后动态取色覆盖主色，但**强调色与语义色仍由我们控制**，避免"danger 按钮变成绿色"这类事故。
- 深色模式不在这里讨论：它是默认跟随系统的，不属于"风格选项"。

### 由此产生的硬约束

- **Android 15 起对 targetSdk 35 的应用强制 edge-to-edge**（内容延伸到状态栏与手势条之下），SafeArea 不是可选项，必须从一开始按"沉浸式 + 安全区避让"设计。这是平台要求，不是风格选择。
- **设计规格集中一份**（配色表、间距刻度、字号阶梯、圆角阶、动效曲线与时长），两端只做"翻译"不做"发挥"。这是"两套 UI 不分叉"的唯一保障。
- 由于两端视觉要一致，**Windows 端不允许为了"更像原生"而偏离规格**——想偏离就得先改规格，而改规格意味着两端一起改。**唯一例外是上面两条让步**：密度用 Dense 变体、标题栏与窗口边框走原生。
